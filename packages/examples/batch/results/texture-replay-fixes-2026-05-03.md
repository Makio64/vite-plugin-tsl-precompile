## Fix 1 — `texture.updateMatrix()` parity with stock TSL

**Symptom.** `webgpu_textures_anisotropy.html.replay` rendered the ground as a uniform brown blur (capture: sharp repeating planks with anisotropy contrast).

**Root cause.** Stock three.js's `TextureNode.update()` ([three.js TextureNode.js:834-845](../../../../three.js/src/nodes/accessors/TextureNode.js)) calls `texture.updateMatrix()` every frame. The slim runtime never builds `TextureNode`s — it goes straight from the captured `material.<prop>.matrix` slot to a UBO write via two writers, both of which read `texture.matrix` *without* first calling `updateMatrix()`. So `texture.repeat.set(512,512)` set on the live cubemap never propagated to the GPU UV-transform matrix; UVs stayed in `[0,1]` → no tiling → glancing-angle GPU samples collapse to the smallest mip.

**Files changed:**
- [packages/runtime/src/hydrator.js](../../../runtime/src/hydrator.js) — `writeMaterialValue()` JIT path now calls `materialValue.updateMatrix()` when `matrixAutoUpdate === true` before reading `materialValue.matrix`.
- [packages/plugin/src/emit-updater.js](../../../plugin/src/emit-updater.js) — AOT emitter prepends `material.<prop>.updateMatrix()` to the emitted `writeMat3` line.
- [packages/runtime/build/three.webgpu.slim.js](../../../runtime/build/three.webgpu.slim.js) — slim bundle rebuilt.

**Verification.** `webgpu_textures_anisotropy.html`: 15.91 dB → **59.53 dB** (replay shows correct repeating wood planks with sharp anisotropy=16 vs blurry anisotropy=1 contrast).

## Fix 2 — Material constructor params + EXR loader callback

**Symptom.** `webgpu_materials_matcap.html.replay` rendered the LeePerrySmith head as a flat near-white silhouette (capture: full sphere-mapped matcap shading with normal-map detail).

**Root causes (two independent bugs in the same example):**

### 2a. Constructor params dropped
The replay-mode wrapper class generated by `slimWebgpuReplayModule()` had:
```js
export class MeshMatcapNodeMaterial {
    constructor() {                              // ← no params
        return __takeMaterial( "MeshMatcapNodeMaterial" );
    }
}
```
The matcap example uses `new MeshMatcapNodeMaterial({ matcap, normalMap, color })` — constructor args dropped on the floor → `material.matcap` and `material.normalMap` left null → 1×1 white fallback for both texture bindings.

### 2b. EXRLoader's `texData` argument dropped by the loader patch
`patchLoaders` wraps the `onLoad` callback of `TextureLoader`/`CubeTextureLoader`/`DataTextureLoader`/`ImageBitmapLoader` to register live textures. The wrapper signature was `(texOrImage) => onLoad(texOrImage)` — only one argument. EXRLoader extends DataTextureLoader and calls `onLoad(texture, texData)`. The wrapper dropped `texData`. Inside EXRLoader's internal `onLoadCallback` ([EXRLoader.js:3407](../../../../three.js/examples/jsm/loaders/EXRLoader.js)): `texture.colorSpace = texData.colorSpace` → `TypeError: Cannot read properties of undefined (reading 'colorSpace')`.

**File changed:**
- [packages/examples/batch/run-e2e.mjs](../../run-e2e.mjs)
  - `slimWebgpuReplayModule()` — stub class accepts a `params` object and assigns each defined key onto the returned material (mirrors three.js's `Material.setValues(...)`).
  - `patchLoaders()` — wrapper now spreads through every argument: `(texOrImage, ...rest) => onLoad(texOrImage, ...rest)`.

**Verification.** `webgpu_materials_matcap.html`: 15.9 dB → **103.01 dB**.

## Fix 3 — PMREM wiring for `material.envMap` and `scene.backgroundNode` (partial)

**Symptom.** `webgpu_pmrem_cubemap.html.replay` rendered as a 6×5 grid of flat white spheres on a black background (capture: warm PMREM-lit chrome→matte spheres on a warm gradient).

**Root cause.** This example never sets `scene.environment` or `scene.background`. Instead:
- `scene.backgroundNode = pmremTexture(map, normalWorldGeometry, uniform(0.5))` — a TSL node carrying the cubemap.
- 30 sphere materials: `new MeshPhysicalNodeMaterial({ envMap: map })`.

Both PMREM-wiring functions in the harness early-returned:
- `__wireBackgroundTextures` requires `scene.background.isTexture`.
- `__wireEnvironmentPMREM` requires `scene.environment.isTexture`.

Plus: HDRCubeTextureLoader (which loads `map`) finishes loading **after** the first render, so `precompileAuxiliary` (gated on `__tslpAuxStarted` first-render-only) missed the background-aux capture entirely → no background artifact at all.

**Files changed (all in `run-e2e.mjs`):**

1. **`__findTextureInNode(node)`** — recursive walker for TSL nodes, looks for any `.value` / `_value` / `texture` / `_texture` / nested-node slots holding a Texture/CubeTexture. Used to recover the cubemap from `scene.backgroundNode = PMREMNode(map, …)` style code.

2. **`__prepareSceneForReplay()`** — recovers the source cubemap from `scene.backgroundNode` *before* replacing it with the stub, stashes in `__capturedBackgroundSource`.

3. **`__wireBackgroundTextures()`** — falls back to `__capturedBackgroundSource` when `scene.background` is missing.

4. **`__wireEnvironmentPMREM()`** — no longer requires `scene.environment`. Walks each PrecompiledMaterial and prefers `material.envMap`'s PMREM (from the per-material kick below) over the scene-level one. **This is the change that made the spheres reflect.**

5. **`render()` post-render kick** — also walks `scene.traverse()` for every PrecompiledMaterial whose artifact needs PMREM, kicks `__kickPMREMGenAsync` for unique `material.envMap` cubemaps, and falls back to `__capturedBackgroundSource` when `scene.background` is absent.

6. **Capture-side re-trigger** — `WebGPURenderer.render()` (capture pass) now re-runs `precompileAuxiliary` whenever `scene.backgroundNode` or `scene.environment` transitions to a new value after the first render. Async loaders that finish post-first-render (HDR/EXR) now get their background-aux artifact captured.

7. **`packages/runtime/src/slim-stubs.js`** — production-slim `pmremTexture(source, ...)` retains the source texture in a module-internal WeakMap (the slim stub is a Proxy, so the carrier can't live on it directly). Exposed via `__getPmremStubSource()`. Slim bundle rebuilt.

**Verification.**
- Spheres: ✅ all 30 now render correct chrome→matte PMREM reflections matching the capture exactly.
- Background: ❌ still wrong (currently white instead of black, but neither matches the warm gradient capture).
  - PSNR: 6.6 → 9.5 dB (~3 dB gain from the spheres).
  - Underlying issue: `PMREMGenerator.fromCubemap(hdrCubeTexture)` running in `__generatePMREMAsync` throws `Cannot set properties of undefined (setting 'material')`. The captured background-aux artifact's WGSL declares a `texture_2d` with `mapping=306` (CubeUVReflectionMapping / `PMREM.cubeUv`), so it needs a PMREM-prefiltered 2D texture. Without a working PMREM, falling back to the raw cube is invalid (cube → 2D binding → WebGPU validation rejects). Separate issue — likely an HDR-format / shared-device incompatibility in `PMREMGenerator.fromCubemap` when the source comes from `HDRCubeTextureLoader`.

## Parallel runner

Added [packages/examples/batch/run-e2e-parallel.mjs](../../run-e2e-parallel.mjs) and a `--report=` flag on `run-e2e.mjs` so each worker writes its own report, and the orchestrator merges them into `results/e2e-report.json`. Two new scripts:

- `pnpm test:e2e` (now defaults to parallel, was serial)
- `pnpm test:e2e-serial` (preserves the old serial path)

**Concurrency note:** 32 workers overran resources (Playwright browser-context exhaustion / OS file-descriptor limits). 8 workers is the safe default; 16 may work on a fresh boot. The orchestrator launches one Chromium per worker so concurrency is gated by host RAM/CPU, not by the test count.

Per-worker report files (`e2e-report-worker-*.json`) are now gitignored — only the merged `e2e-report.json` is tracked.
