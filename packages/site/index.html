vite-plugin-tsl-precompile

Precompile three.js TSL materials before they reach your users.

Add .precompile('name') to a TSL material. In dev, the plugin captures a shader artifact. In build, it inlines static WGSL and a generated uniform updater into your app bundle.

Get started Examples gallery → How it works View on GitHub

the one line you add

// your source, unchanged three.js TSL
const water = new MeshStandardNodeMaterial();
water.colorNode = mix(color('#002'), color('#4af'), uv().y);
water.precompile('ocean-water');   // ← the only addition

Keep authoring normal three.js TSL. The marker tells the plugin which materials to bake.

how it works

Four steps, one round trip.

Want a friendlier tour with mini animated schemas? See the class-by-class walkthrough →

  1. 1

    Mark material

    material.precompile('name') is the opt-in marker. Use a stable static string for each material you want baked.

  3. 2

    Run dev once

    Open the app in dev. The marker runs the real three.js node builder on the live material and writes artifacts/<name>.<hash>.json.

  5. 3

    Build rewrites

    Production build rewrites .precompile('name') to __applyPrecompiled(...) and imports the baked artifact through a virtual module.

  7. 4

    Users get baked shaders

    The final app bundle contains static WGSL and the generated updater. No separate artifact JSON is requested by the browser.

five staleness gates

Shaders never silently drift.

Any single failure stops the build or app init.

  • 1

    Content hash

    sha256 over the normalized TSL graph, three.js version, and plugin version.

  • 2

    Dev hot re-extract

    File save re-runs the extractor; the dev server HMRs the new artifact.

  • 3

    Build hash check

    The transform compares the committed hash to the one emitted at build. Mismatch is a hard error.

  • 4

    Runtime assertion

    __applyPrecompiled asserts the artifact hash at app init, before the first frame.

  • 5

    CI verify

    pnpm verify wipes artifacts/, re-extracts in a Node harness, and diffs against the committed set.

get started

Add to an existing Vite + three.js project.

The plugin does one job: it turns selected TSL materials into build-time artifacts, then ships those artifacts inside your production bundle.

Prereqs Node ≥ 20.19 pnpm 10 (or npm / yarn) Vite 5+ · three 0.184+ WebGPU browser — Chrome/Edge 113+, Safari TP

Missing any of those? Fix them first — the rest won't work without them.

Smaller runtime

Marked materials can run through the slim path instead of shipping the full node-builder path to users.

Faster startup

The expensive TSL graph walk and WGSL generation happen before production, not during the first user render.

Safer deploys

Hash checks catch stale artifacts during build or app init instead of letting shader drift ship silently.

Setup Five steps

1. Install the plugin and runtime

pnpm add -D vite-plugin-tsl-precompile @tsl-precompile/runtime

vite-plugin-tsl-precompile runs inside Vite during dev and build. @tsl-precompile/runtime provides the marker, runtime wrapper, and slim path used by the generated bundle.

2. Register in vite.config.js

import { defineConfig } from 'vite';
import tslPrecompile from 'vite-plugin-tsl-precompile';

export default defineConfig({
  plugins: [
    tslPrecompile({
      artifactsDir: './artifacts',
    }),
  ],
});

3. Mark one material in your source

import { MeshStandardNodeMaterial } from 'three/webgpu';
import { mix, color, uv } from 'three/tsl';

const water = new MeshStandardNodeMaterial();
water.colorNode = mix(color('#002'), color('#4af'), uv().y);
water.precompile('ocean-water');

mesh.material = water;

The name must be a literal string. Treat it like a stable artifact id for that material.

4. Run dev and visit the page once

pnpm dev

The marker only captures after the material is actually created in the browser. When it works, you will see artifacts/<name>.<hash>.json in your configured artifactsDir. Commit that folder.

5. Build for production

pnpm build

The build consumes the committed artifact JSON and inlines it into the final JS bundle. Users do not download the JSON files separately.

Verify it worked

  • Dev server log shows [tsl-precompile] captured <name> → artifacts/<name>.<hash>.json.
  • A file artifacts/<name>.<hash>.json exists in your configured artifactsDir.
  • Saving the material source triggers an HMR re-capture with a new hash.

If all three happen, you're good. The committed artifacts/ files are the source for the production rewrite.

What ships to users?

Your production bundle ships static WGSL, generated uniform-update code, and the slim runtime path. The checked-in artifact JSON is build input, not a browser request.

troubleshooting

Things that trip people up.

"WebGPU not available" in the console

The runtime needs a WebGPU-capable browser. Use Chrome/Edge 113+ (stable) or Safari Technology Preview. Confirm your browser actually has a working adapter at about://gpu — look for WebGPU: Hardware accelerated. If you're on Firefox or Safari stable, WebGPU isn't fully wired up yet.

The artifacts/ folder is empty after pnpm dev

The extractor only runs when material.precompile('…') is actually reached at runtime. Open the page in the browser (a cold pnpm dev with no visit won't capture anything). Confirm the marker is on a code path that executes — not hidden behind a feature flag or a component that was never mounted.

"hash mismatch" error at build

The committed artifact and the source TSL graph have drifted. Run pnpm dev, visit the page once to re-capture, commit the updated artifacts/<name>.<hash>.json, then rebuild. This is Gate 3 from the staleness gates doing its job.

Should I commit the artifacts/ folder?

Yes — always. Those files are your baked shaders and bindings. The build fails without them because there's nothing to inject into the slim runtime. Treat them like generated code you check in, similar to lockfiles.
