Same pixels. Less work.

Precompiling doesn't change what you see — it changes what runs. The slim runtime ships the already-compiled WGSL, so it's smaller on the wire, pixel-identical, and skips the first-frame compile that stock three.js pays in the browser. Two of those are measured offline below; the third you can measure on your own GPU.

How this is measured (and what it doesn't measure)

For each scene we build the TSL material with stock three/webgpu, then time the cold first renderAsync — which walks the node graph and compiles the WGSL pipeline — against the trimmed median of 90 steady-state frames after a 40-frame warm-up. A precompiled / slim build ships the compiled WGSL, so its first frame costs about the steady-state number; the cold→steady delta is the compile cost it removes.

Caveats: this is JS-side wall time around renderAsync, not isolated GPU time; numbers vary by GPU, driver and thermal state; the steady frame is used as the no-compile floor rather than a separate slim render. It measures the first-frame win — the per-draw win (straight-line UBO writes vs node-graph traversal) is real but smaller and not isolated here. The bundle and pixel-identical numbers above are the hard comparative evidence.

The honest tradeoff: the node→WGSL compiler still lives in the bundle today — the win is that it never runs in production (no first-frame stall, no per-draw graph traversal), and the output is byte-for-byte the same. How it works →
