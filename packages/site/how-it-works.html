a quiet little plugin

Why does the browser
compile your shaders?

We did it on your machine instead. One line of code.

today

Every visitor waits for the shader to compile.

compiling shader…
~2 MB three.js bundle, including the shader builder
first-frame stall while the GPU pipeline gets built

the fix

We move the work
from the user's browser
to your build.

the flow

One piece of work, four stages.

You write

.precompile('ocean') on a normal material.

Dev bakes

Open the page once. The shader gets saved to disk.

Build packs

The saved shader goes into your bundle.

User runs

No shader compile, smaller bundle.

From your editor to the user's GPU. Each stage is a small file you'll meet below.

what you get

Three concrete benefits.

full three.js ~2 MB
slim runtime ≤ 350 KB

Smaller bundle

The shader builder is the heavy part of three.js. We don't ship it — only the slim bits that play back the saved shader.

no compile

Faster first frame

The expensive walk through your TSL graph happens once on your machine. Users see the result instantly.

Safer deploys

Every saved shader has a fingerprint. If your code drifts from the saved file, the build stops. No silent breakage.

the catch

It's literally one line.

// your normal three.js TSL material
const water = new MeshStandardNodeMaterial();
water.colorNode = mix(color('#002'), color('#4af'), uv().y);
water.precompile('ocean');  // ← the only addition
mesh.material = water;

No other change. No new APIs. Same three.js.

behind the scenes

Which file does what?

Eight little files do the whole job. Four run on your machine while you develop. Four travel with your app to the user.

While you develop

precompile-marker.js

Adds .precompile('name') to materials. The one line you write.

dev-capture-server.js

In dev, saves the baked shader to artifacts/<name>.<hash>.json.

three-rewrite.js

At build, swaps each .precompile('ocean') for "load the saved file."

emit-updater.js

Generates a tiny per-material function that pushes its values to the GPU.

While users use it

apply-precompiled.js

At startup, plugs the saved shader in. Build fails loudly if the fingerprint is stale.

PrecompiledMaterial

Drop-in material that tells three.js "shader's already done — skip building."

writers.js

Each frame, pushes the changing values (camera, time, color) to the GPU.

slim-entry.js

A three.js without the shader-builder. Smaller bundle, less to parse.

the journey of one material

Five steps. In order.

  1. 1

    You add the marker

    water.precompile('ocean'). Everything else stays normal.

  2. 2

    Dev bakes it once

    Open the page. The marker hands the finished shader to the helper.

  3. 3

    A new file appears

    artifacts/ocean.<hash>.json shows up. Commit it.

  4. 4

    Build inlines it

    The plugin swaps your line for "load the saved file" and packs the shader into your bundle.

  5. 5

    Users get fast frames

    The browser sees "shader's done" and skips compiling. First render is instant.

try it

Four small steps.

Once. Then it's just .precompile('name') on each material you want baked.

  1. 1

    Install the packages

    pnpm add -D vite-plugin-tsl-precompile @tsl-precompile/runtime
  2. 2

    Register the plugin in vite.config.js

    import { defineConfig } from 'vite';
import tslPrecompile from 'vite-plugin-tsl-precompile';

export default defineConfig({
  plugins: [ tslPrecompile({ artifactsDir: './artifacts' }) ],
});
  3. 3

    Mark a material

    water.precompile('ocean');  // the rest of your three.js code stays the same
  4. 4

    Bake, then ship

    pnpm dev    # open the page once — saves artifacts/ocean.<hash>.json
pnpm build  # inlines the saved shader into your bundle

Commit the artifacts/ folder. Treat it like generated source — the build needs it.
